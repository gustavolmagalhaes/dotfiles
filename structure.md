# NixOS Configuration Structure Guide

This document explains the architecture, design principles, and directory layout of this NixOS configuration, modeled after [afsc19/nixos-config](https://github.com/afsc19/nixos-config) and [diogotcorreia's dotfiles](https://github.com/diogotcorreia/dotfiles).

---

## 1. High-Level Architecture & Philosophy

The configuration enforces a strict **separation of concerns** divided into five main concepts:

| Concept | Directory | Purpose | Declares Options? |
| :--- | :--- | :--- | :--- |
| **Engine / Helpers** | `lib/` | Implements auto-discovery (`rakeLeaves`), system generators (`mkHosts`), and package sets (`mkPkgs`). | No |
| **Modules** | `modules/` | Reusable units of functionality (services, apps, shell setups) with toggleable settings. | **Yes** (`options.modules...`) |
| **Profiles** | `profiles/` | Pre-defined roles or collections of modules and packages (e.g. `graphical.niri`, `shell.essential`). | **No** (Imports only) |
| **Hosts** | `hosts/` | Machine-specific declarations. Each host imports profiles and sets hardware/network parameters. | No |
| **Static Assets** | `config/` | Non-Nix configuration files (e.g., KDL, CSS, wallpapers) symlinked into the target system. | No |

## 3. Core Components Explained

### 3.1. `lib/`: The Automatic Engine

The files in `lib/` eliminate manual `import` boilerplate:

- **`lib/importers.nix` (`rakeLeaves`)**:
  Recursively traverses a folder and produces a nested attribute set mirroring the folder structure. Leaves are `.nix` file paths (or folders containing a `default.nix`).
- **`lib/generators.nix`**:
  - `mkProfiles`: Rakes `profiles/` so you can reference any profile via `profiles.<folder>.<name>`.
  - `mkHosts`: Reads `hosts/`. For every folder (e.g. `hosts/ace`), it constructs a NixOS configuration named after the folder (`nixosConfigurations.ace`).
  - `mkHost`: Automatically collects and imports **every module in `modules/`** into the NixOS system:
    ```nix
    modules = (lib.collect builtins.isPath (rakeLeaves ../modules))
      ++ [ { networking.hostName = hostname; } hostPath ]
      ++ extraModules;
    ```
- **`lib/default.nix`**:
  Merges all functions in `lib/` into `lib.my`.

---

### 3.2. `modules/`: Modular Options & The `hm` Bridge

In traditional NixOS configs, Home Manager requires a separate configuration tree (e.g. `home-manager.users.<user>`). This leads to fragmented configurations where the system part of an app lives in one file and the user part lives in another.

#### The `modules/home.nix` Bridge
`modules/home.nix` introduces two alias options:
- `options.hm`: Aliased directly to `home-manager.users.${user}`.
- `options.usr`: Aliased directly to `users.users.${user}`.

```nix
config = {
  home-manager.users.${user} = mkAliasDefinitions options.hm;
  users.users.${user} = mkAliasDefinitions options.usr;
};
```

#### How Modules Work
Because of this bridge, **any module can configure both NixOS and Home Manager in the same file**:

```nix
# Example: modules/graphical/terminal/ghostty.nix
{ config, lib, pkgs, ... }:
let
  cfg = config.modules.graphical.terminal.ghostty;
in
{
  # 1. Declare the toggleable option:
  options.modules.graphical.terminal.ghostty.enable = lib.mkEnableOption "Ghostty Terminal";

  # 2. Implement system or Home Manager configuration when enabled:
  config = lib.mkIf cfg.enable {
    hm.programs.ghostty = {
      enable = true;
      package = pkgs.ghostty;
      settings = { ... };
    };
  };
}
```

> **Rule:** Every module declares an option under `modules.<category>.<name>.enable` and guards its configuration with `lib.mkIf cfg.enable`.

---

### 3.3. `profiles/`: Role Presets (No Options)

Profiles are **opinionated selections** of modules and packages meant for a specific workflow or machine role.

- Profiles **never** declare `options.modules...`.
- Profiles simply turn modules on (`modules.foo.enable = true;`) and add relevant package bundles (`environment.systemPackages = [ ... ];`).
- Profiles are imported into hosts using the `profiles` attribute set passed to each host:
  ```nix
  imports = with profiles; [
    graphical.niri
    graphical.browsers
    shell.essential
  ];
  ```

---

### 3.4. `hosts/`: Machine Definitions

Each machine has its own directory inside `hosts/` (e.g., `hosts/ace`).

- **`default.nix`**:
  Imports the desired profiles and defines machine-specific parameters:
  - Bootloader settings (`boot.loader...`)
  - Timezone and locale (`time.timeZone`, `i18n...`)
  - Keyboard layout (`services.xserver.xkb...`, `console.keyMap`)
  - Host-specific overrides.
- **`hardware-configuration.nix`**:
  The hardware scan generated by `nixos-generate-config`. Any `.nix` file in the host directory (other than `default.nix`) is automatically imported by `generators.nix`.

---

### 3.5. `config/`: Non-Nix Static Assets

Configuration files like Niri's `config.kdl` or custom scripts are kept in `config/`:
- `flake.nix` passes `configDir = ./config;` via `extraArgs` to all modules.
- Modules reference these files cleanly without hardcoded relative paths:
  ```nix
  hm.xdg.configFile."niri/config.kdl".source = "${configDir}/niri/config.kdl";
  ```

## 4. How diogotcorreia & afsc Create Modules, Apps & Packages

The architecture follows a strict decision rule for adding new software:

> **Rule of Thumb:**
> - If an app requires **configuration, dotfiles, daemon services, kernel modules, or firewall rules**, create a **Module** in `modules/`.
> - If an app is just an **unconfigured package** (or a set of tools you want installed together), add it directly to a **Profile** in `profiles/`.
> - If an app is **not available in nixpkgs**, create a derivation in `packages/` or add an overlay in `overlays/`.

---

### 4.1. Pattern 1: Creating a New Module (`modules/`)

Modules declare toggleable options and define implementation. Thanks to `generators.nix` and `rakeLeaves`, **any `.nix` file placed in `modules/` is automatically imported into every host**. You never need to manually register a new module file.

Every module adheres to this 4-part structure:
1. Receives `{ config, lib, pkgs, ... }` (plus `configDir`, `user`, `userFullName` via `extraArgs`).
2. Extracts its config: `cfg = config.modules.<category>.<name>;`.
3. Declares an enable option: `options.modules.<category>.<name>.enable = lib.mkEnableOption "...";`.
4. Wraps configuration in `config = lib.mkIf cfg.enable { ... };`.

#### Case A: Simple Graphical App (e.g. Stremio)
When an application is installed via Home Manager for the user:
```nix
# modules/graphical/apps/stremio.nix
{ config, lib, pkgs, ... }:
let
  inherit (lib) mkEnableOption mkIf;
  cfg = config.modules.graphical.apps.stremio;
in
{
  options.modules.graphical.apps.stremio.enable = mkEnableOption "Stremio";

  config = mkIf cfg.enable {
    # 'hm' is the Home Manager alias from modules/home.nix
    hm.home.packages = with pkgs; [
      stremio-linux-shell
    ];
  };
}
```

#### Case B: Graphical App with System Integration (e.g. OBS Studio)
A single module can configure **system-level** settings (kernel modules, firewall) and **Home Manager** settings simultaneously:
```nix
# modules/graphical/apps/obs.nix
{ config, lib, pkgs, ... }:
let
  inherit (lib) mkEnableOption mkIf;
  cfg = config.modules.graphical.apps.obs;
in
{
  options.modules.graphical.apps.obs.enable = mkEnableOption "OBS Studio with virtual camera";

  config = mkIf cfg.enable {
    # System level: load v4l2loopback kernel module for virtual camera
    boot.extraModulePackages = [ config.boot.kernelPackages.v4l2loopback ];
    boot.extraModprobeConfig = ''
      options v4l2loopback devices=1 video_nr=10 card_label="OBS Virtual Camera" exclusive_caps=1
    '';

    # User level: install OBS with plugins for user
    hm.home.packages = [
      (pkgs.wrapOBS {
        plugins = with pkgs.obs-studio-plugins; [
          obs-backgroundremoval
        ];
      })
    ];
  };
}
```

#### Case C: Program with Dedicated Home Manager Module (e.g. Ghostty / VSCode)
When Home Manager already provides built-in options (`programs.<name>`):
```nix
# modules/graphical/terminal/ghostty.nix
{ config, lib, pkgs, ... }:
let
  inherit (lib) mkEnableOption mkIf;
  cfg = config.modules.graphical.terminal.ghostty;
in
{
  options.modules.graphical.terminal.ghostty.enable = mkEnableOption "Ghostty Terminal";

  config = mkIf cfg.enable {
    hm.programs.ghostty = {
      enable = true;
      package = pkgs.ghostty;
      settings = {
        theme = "Abernathy";
        font-family = "JetBrainsMono Nerd Font";
        font-size = 11;
        window-decoration = false;
      };
    };
  };
}
```

#### Case D: App with Static Config Files from `config/` (e.g. Niri)
Use the `configDir` parameter passed automatically from `extraArgs`:
```nix
# modules/graphical/niri.nix
{ config, lib, pkgs, configDir, ... }:
let
  cfg = config.modules.graphical.niri;
in
{
  options.modules.graphical.niri.enable = lib.mkEnableOption "Niri Compositor";

  config = lib.mkIf cfg.enable {
    programs.niri.enable = true;

    # Symlink dotfiles from config/
    hm.xdg.configFile."niri".source = "${configDir}/niri";
  };
}
```

### 4.2. Pattern 2: Adding Packages via Profiles (`profiles/`)

Not every program needs a dedicated module. If you just want utilities or simple desktop tools available without custom settings, **add them directly to a profile**.

#### Example 1: Bundling Simple Tools in an Existing Profile
In `profiles/shell/essential.nix`, diogotcorreia and afsc add all CLI tools together:
```nix
{ pkgs, ... }:
{
  # 1. Enable relevant modules
  modules.shell = {
    zsh.enable = true;
    git.enable = true;
  };

  # 2. Add unconfigured packages directly
  environment.systemPackages = with pkgs; [
    fastfetch
    nnn
    btop
    ripgrep
    jq
    tree
  ];
}
```

#### Example 2: Creating a Dedicated Preset Profile
For a group of related apps (e.g., disk utilities or games):
```nix
# profiles/graphical/disk-utils.nix
{ pkgs, ... }:
{
  environment.systemPackages = with pkgs; [
    gparted
    baobab          # Disk usage analyzer
    gnome-disk-utility
  ];
}
```

### 4.3. Pattern 3: Activating in Hosts (`hosts/`)

Once a module or profile exists, a host enables it in `hosts/<hostname>/default.nix`:

#### Approach 1: Import the Profile (Recommended)
```nix
{ profiles, ... }:
{
  imports = with profiles; [
    graphical.niri
    graphical.browsers
    graphical.terminals
    shell.essential
  ];
}
```

#### Approach 2: Toggle Specific Modules Directly
If a specific machine needs an extra app that isn't part of a general profile:
```nix
{ ... }:
{
  modules.graphical.apps.obs.enable = true;
  modules.graphical.apps.stremio.enable = true;
}
```

---

### 4.4. Pattern 4: Custom Packages Not in Nixpkgs (`packages/` & `overlays/`)

When software isn't available in official Nixpkgs:

1. **Create the package derivation in `packages/<name>.nix`**:
   ```nix
   # packages/my-tool.nix
   { lib, stdenv, fetchFromGitHub }:
   stdenv.mkDerivation {
     pname = "my-tool";
     version = "1.0.0";
     # ...
   }
   ```
2. **Expose it via an overlay in `overlays/packages.nix`**:
   ```nix
   # overlays/packages.nix
   let packagesDir = ../packages; in
   { lib, ... }:
   _final: prev: {
     my = lib.packagesFromDirectoryRecursive {
       inherit (prev) newScope callPackage;
       directory = packagesDir;
     };
   }
   ```
3. **Use it anywhere**:
   Available as `pkgs.my.my-tool` in any module or profile.

### 4.5. Summary Cheat Sheet

| Task | Where it goes | Example |
| :--- | :--- | :--- |
| **New tool with config/settings** | `modules/<category>/<tool>.nix` | Declare `options.modules.<category>.<tool>.enable` and configure `hm.programs.<tool>`. |
| **GUI app with firewall/drivers** | `modules/graphical/<tool>.nix` | Combine `boot.*`, `networking.firewall.*` and `hm.home.packages = [ pkgs.<tool> ];`. |
| **Just install a CLI or GUI tool** | `profiles/<category>/<profile>.nix` | Add package name to `environment.systemPackages = with pkgs; [ <tool> ];`. |
| **Turn on a set of tools for a machine** | `hosts/<machine>/default.nix` | Add the profile to `imports = with profiles; [ ... ];`. |
| **Custom package derivation** | `packages/<name>.nix` | Call via `pkgs.my.<name>` in any module or profile. |

## 5. Maintenance Commands

- **Verify configuration syntax and evaluate system derivations:**
  ```bash
  nix flake check
  ```
- **Rebuild and activate the system:**
  ```bash
  sudo nixos-rebuild switch --flake .#ace
  ```
- **Test without adding to bootloader menu:**
  ```bash
  sudo nixos-rebuild test --flake .#ace
  ```
- **Update flake inputs:**
  ```bash
  nix flake update
  ```
